Ghost Trader

I gave 80 trading bots $1,000 of imaginary money each, pointed them at real live markets, and let them disagree with each other for weeks. The goal was $10,000.

It did not get to $10,000. That turned out to be the interesting part.

6,270 lines of Python/ 170 tests/ 2 dependencies/ 5 markets/ no real order was ever placed
01/What we are betting on

On Polymarket, the price is the probability.

A share in “Yes” pays exactly $1 if the event happens and $0 if it doesn’t. So a share trading at 61¢ means the crowd thinks there’s a 61% chance.

That makes it the cleanest possible lab. Unlike a stock, every bet gets a definitive right-or-wrong answer, usually within days — so you can actually score a strategy instead of arguing about it.

The hypothesis under test
Traders who bet $1,000+ in a single order know something the price doesn’t.

The plan → watch every trade on the exchange. When someone bets big, look up that wallet’s history. Copy wallets that have been right more than 60% of the time. Bet against wallets under 40%. Ignore everyone else.

Scoring uses only bets that had already resolved before the signal arrived — otherwise you’re grading with tomorrow’s newspaper.

Data source: Polymarket public trade feed + Gamma markets API/polled every 20s
02/Architecture

One feed. Eighty opinions.

poller One process fetches the live trade feed. Every bot sees the identical tick.
→
scorecard Size-weighted win rate per wallet. 48 wallets scored so far.
→
strategy ×80 Each variant answers copy, fade, explore, or skip — with a reason.
→
risk Position sizing and exposure caps, deliberately kept separate from strategy.
→
paper book Fake cash, real prices. Settles at $1 or $0 when the market resolves.

Why one poller and not eighty?

It’s 1× the API load instead of 80×, so nothing gets rate-limited. But mainly: if each bot fetched separately they’d see slightly different prices at slightly different moments, and the results would differ because of network luck rather than strategy. Shared data is what makes the comparison fair.

State is a plain JSON file.

Every position, every settled trade, every wallet score. Kill the process, restart it, and it resumes mid-experiment. The dashboard is a separate read-only reader of that same file, so watching the bots can never disturb them.

Python 3.9/dependencies: requests, PyYAML/no database, no broker, no framework
03/The decision, in code

The bot has to explain itself — even when it does nothing.

Most of this function is the rejections. Every signal returns an Evaluation with a plain-English reason, whether it traded or not.

That log is not a nicety. 239 recorded rejections are how I later found out that scouting bets were quietly eating every slot, and that the strategy I was actually testing had stopped firing days earlier.

Sizing lives somewhere else on purpose. “Should we bet?” and “how much?” are different questions, and mixing them is how you end up unable to tell which one was wrong.

04/Experiment design

One bot is an anecdote.

“Explore” is the control. A flat $15 bet on any big trade from a wallet the bot had never seen — no judgement at all. It beat the strategy.

The bot bet twice as much on the signal it was right about less often — and lost 3.7× more when it was wrong.

The mechanism → base = equity × max_pct × confidence. Confidence came from track record, so a “trusted” wallet automatically got a bigger stake. Sizing doesn’t create edge — it multiplies what you already have. This lost on size and asymmetry, not accuracy.

06/Finding two

The bigger the bet, the worse it did.

Same strategy, five different bars for “this is a whale.” Following $500 bets won 68% of the time. Following $10,000 bets won 44% — worse than a coin flip.

A plausible reading: a $10,000 single order is more often a hedge, a longshot punt, or someone with more money than information. The sharp trader is sizing sensibly — so “biggest” is a bad proxy for “smartest.”

Correlation, threshold vs. return, across 20 bots: −0.376/ Caveat: the $10k bucket is 27 bets — the trend is real in this data, it is not yet proof
07/Finding three/the other four markets

56 bots, four asset classes, no separation.

one strategy bot buy-and-hold control — buys once, then does nothing

Momentum, mean-reversion, breakout, volatility-scaled, take-profit variants — every one of them lands within 0.7 percentage points of flat, with the do-nothing control sitting comfortably mid-pack. In crypto, which has the most completed trades (112 round trips), the momentum bots are winning only 9–28% of them: they buy every wiggle and get chopped to pieces by fees. Honest caveat: stocks and forex have barely traded (7 round trips between them). This is “no separation yet,” not “proven no edge.”

08/What actually went wrong

A broken trading bot still reports numbers.

  1. Nothing ever finished. 218 open positions, zero resolutions — the markets API hides closed markets by default. one retry with closed=true → 146 resolutions appeared instantly
  2. The strategy never ran. The scorecard didn’t save in-flight bets, so every restart wiped it to zero wallets scored. Copy and fade hadn’t fired in days. running perfectly, testing nothing
  3. The value bots became longshot bots. Ranking by absolute edge always picks the cheapest side. Average entry drifted to 29¢. Down $247. fixed with relative edge + a price floor
  4. The retry that never gave up. The error path used continue, which skips the exit check at the bottom of the loop. a blocked feed retried forever; now exits cleanly in 3 seconds
Not one of these crashed. Every one produced a confident, plausible, completely meaningless number.

In normal software a bug is loud — something throws, something 500s, a test goes red. In a trading system the bug is silent, because a portfolio that never resolves anything and a portfolio that’s genuinely flat look identical from the outside.

All four were found by reading the log of decisions not taken, not by watching the P&L. The P&L looked fine. It was fine. It was also fiction.

09/Five things worth stealing

What I’d do the same, and what I’d do differently.

  1. Always ship the do-nothing control. Buy-and-hold costs ten lines, and it is the only thing that tells you whether your strategy is skill or weather.
  2. Log the decisions you didn’t take, with reasons. The rejections are the dataset. My three worst bugs were invisible in the results and obvious in the reject log.
  3. Separate “should I?” from “how much?” Sizing multiplies your signal; it never creates one. Scaling stake by confidence turned a mildly bad signal into a −$671 one.
  4. Test the failure path, not the happy path. Every bug here lived in an except branch or a default API parameter — places the happy-path tests never reach.
  5. n = 45 is not a result. My best bot read +16.3% one week and +1.1% the next, having changed nothing. If I’d presented last week I’d have told you the opposite story with equal confidence.
